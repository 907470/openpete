# Adding a game (Spyro 2, Spyro 3, …)

The recipe for wiring a second PSX title into openpete. `games/spyro-1/` is
the only port that exists; every step below is derived from it.
`games/spyro-2/` and `games/spyro-3/` hold a `TODO.md` and nothing else.

Read the "What is not abstracted yet" section before starting. The
`core/`-to-game boundary is narrower than `core/include/game_extras.h`
suggests, and the codegen scripts are hardcoded to Spyro 1.

## Prerequisites

- A matching-decomp git repo whose `make` produces:
  - a GNU ld linker map (`build/psx.map`) — drives every manifest,
  - `build/PSX.EXE` — the recompiler's main input,
  - the PSYQ object the map places (`build/asm/psyq.o` for Spyro 1),
  - overlay binaries (`build/wad/*.ovl` for Spyro 1) if the title uses
    overlays.
- The original disc BIN/CUE for the title.

## 1. Submodule the decomp

```bash
git submodule add <decomp-url> games/<game>/<game>
```

The nested layout keeps openpete commits separate from decomp commits.
Spyro 1's entry is `games/spyro-1/spyro-1` (`.gitmodules`). The submodule is
read-only from openpete's side; openpete commits never touch files inside
it.

## 2. Skeleton

What `games/spyro-1/` actually carries, reduced to the parts a second game
needs:

```
games/<game>/
├── CMakeLists.txt          # produces the openpete-<game> executable
├── <game>/                 # the decomp submodule
├── manifest/
│   ├── symbols.toml        # function addresses, generated from psx.map
│   ├── globals.toml        # global addresses, generated from psx.map
│   ├── psyq.toml           # PSYQ symbol → address, generated from psx.map
│   ├── native.toml         # hand-curated: which decomp TUs the AST
│   │                       #   rewriter compiles natively, and how
│   ├── prototypes.toml     # hand-curated function signatures
│   └── forced_entries/     # recompiler entry points the scanner misses
├── generated/              # codegen output; gitignored (.gitignore:8)
├── game_extras_impl.c      # implements core/include/game_extras.h
├── feature_list.c          # defines openpete_features[] + the count
├── features/               # per-game feature modules (feature_module_t)
├── main.cpp                # entry point: parse opts, register the game's
│                           #   surfaces with core, call openpete_run
└── <per-game runtime TUs>  # recomp attach, PSYQ thunks, dispatch chain
```

`symbols.toml` and `globals.toml` are generated by
`scripts/regen-manifest.sh` (via `tools/build_manifest.py`) and are
gitignored (`.gitignore:11-12`). `psyq.toml` has its own generator, run when
the decomp's PSYQ object changes:

```bash
python3 tools/gen_psyq_toml.py --exe games/<game>/<game>/build/PSX.EXE \
        games/<game>/<game>/build/psx.map \
        build/asm/psyq.o games/<game>/manifest/psyq.toml
```

`--exe` drops the header's entry, the crt0 the runtime dispatches, from the
stubbed set; `--translate NAME` (repeatable) drops a symbol the crt0 reaches
before `main`, such as `InitHeap`, when the manifest is not filtered with
`--thunked-only`.

The second argument is the object-file name as it appears in the map, not a
path on disk.

There is no `overlays.toml` and no `compat/` directory. Spyro 1's overlay
registry is `generated/spyro_overlay_table.c`, emitted by
`scripts/regen-recomp.sh` and typed by `games/spyro-1/spyro_overlay_table.h`;
PSX globals reach native decomp code through linker `--defsym` aliases into
`g_ram` (`generated/native_aliases.cmake`), and unimplemented PSYQ entry
points through `generated/psyq_stubs.c`. All three are codegen outputs, not
hand-written headers.

The gameplay-state region manifest that the oracle compares lives at the
repo root (`manifest/gameplay_state_regions.toml`), not under `games/`. It is
single-game today; a second game needs it split per game or scoped.

## 3. Implement `game_extras.h`

`core/include/game_extras.h` declares roughly 25 functions. Every one of them
must be defined for the executable to link — there are no weak defaults and
no core-side fallbacks. Identity (`game_get_entry_point`,
`game_get_exe_filename`, `game_get_expected_crc32`, `game_get_display_name`,
`game_get_id`) is the first group to fill in, but a build does not link until
memory layout, overlay hooks, per-tick hooks, savestate hooks, the position
probe, and the CLI-argument resolvers are all present, even as stubs.

```c
uint32_t game_get_entry_point(void) {
    return 0xXXXXXXXXu;  /* PSX.EXE header field initial_pc */
}
```

Spyro 1's implementations are in `games/spyro-1/game_extras_impl.c`.

## 4. Register the game's surfaces with core

`game_extras.h` is not the whole contract. `games/spyro-1/main.cpp` also
hands core these, before `openpete_run()`:

- `openpete_recomp_register()` — the recompiled-code descriptor
  (`core/include/openpete_recomp_module.h`). Core reaches recompiled code
  only through it; dispatch aborts with a message if it was never called
  (`core/runtime/dispatch.c:29`).
- `psx_override_dispatch_game()` — the per-function intercept gate. Declared
  weak in `core/runtime/dispatch.c:323`, defined by the game
  (`games/spyro-1/game_extras_impl.c:597`).
- `openpete_features[]` and `openpete_feature_count`
  (`core/include/feature_registry.h`), defined in `feature_list.c`.
- `openpete_state_regions_register()` (`core/include/openpete_psx.h:135`) —
  the gameplay-state region table the oracle and savestates read.
- `openpete_interp_register_regions()` and
  `openpete_interp_register_obj_capture()` (`core/include/openpete_interp.h`)
  — the sub-tick interpolation tables.
- `openpete_config_set_game_id()` and `openpete_config_set_disc_identity_fn()`
  — the `[game.<id>]` config scope and disc identification.
- `openpete_mods_set_symbol_table()` plus the mod draw-service and content
  registry callbacks, if the game ships the mod SDK.

Spyro 1 registers the interp and state-region tables explicitly rather than
through weak symbols: MinGW's PE/COFF linker mis-resolves weak overrides in
this configuration (`games/spyro-1/main.cpp`).

## 5. Wire it into the top-level build

Append the game name to `OPENPETE_GAMES` in the top-level `CMakeLists.txt:59`:

```cmake
set(OPENPETE_GAMES "spyro-1;<game>" CACHE STRING "Games to build (semicolon-separated)")
```

Or pass it at configure time:

```bash
cmake --preset linux-release -DOPENPETE_GAMES="spyro-1;<game>"
```

`CMakeLists.txt:120` adds `games/<game>/` for each entry that has a
`CMakeLists.txt`, and warns and skips otherwise.

Two build knobs the per-game `CMakeLists.txt` is expected to honour:
`OPENPETE_SKIP_DECOMP` (drop the natively-compiled decomp TUs and route
every vaddr through the recompiler; every release preset sets it ON, e.g.
`cmake/presets/linux-release.cmake:4`) and `OPENPETE_RECOMP_LINKAGE`
(`static` links the recomp module in, `shared` dlopens it and requires
`OPENPETE_SKIP_DECOMP=ON`, `games/spyro-1/CMakeLists.txt:112`).

## 6. Codegen and setup scripts are Spyro-1-specific

These are not parameterized by game and must be generalized or copied:

- `scripts/setup.sh` — hardcodes the SCUS-94228 rebuilt-disc path and the
  `games/spyro-1/spyro-1` submodule path.
- `scripts/regen-manifest.sh` — hardcoded `MANIFEST_DIR`/`GENERATED_DIR`
  under `games/spyro-1/`; defaults `PSX_MAP` to the sibling checkout
  `../spyro-1/build/psx.map`.
- `scripts/regen-recomp.sh` — hardcoded input and output paths under
  `games/spyro-1/`, and Spyro 1's single overlay vaddr `0x8007AA38`.

## 7. What is not abstracted yet

With one port in the tree, several game-specific facts sit in `core/` rather
than behind `game_extras.h`. Named unknowns, not a design:

- The window/taskbar icon is resolved by weak symbols literally named
  `openpete_spyro1_icon_*` (`core/runtime/run.c:2085`).
- The renderer's fallback window title is the string "Spyro the Dragon"
  (`core/runtime/native_render.c:1383`).
- `--render-paths` accepts Spyro-specific path names
  (`core/runtime/options.c:501`), and several `SPYRO_*` rows sit in
  `core/runtime/knob_registry.c`.
- The `core/` purity check (`openpete_core_purity_check` in
  `core/CMakeLists.txt`) only refuses bare `0x800XXXX` address literals and
  Win32-only APIs. It does not refuse a Spyro-specific name, and around
  forty files under `core/` currently contain one.

Which of these become `game_extras.h` hooks and which stay is undecided; the
standing rule is that the abstraction grows when a second game forces it,
not before. Behaviour that can live in `games/<game>/` goes there.
